# TripleG3.P2P Enhancement Review

Review date: 2026-07-27  
Scope: source, public APIs, tests, package metadata, documentation, and GitHub Actions workflows.  
Method: repository inspection followed by a Release solution build and full test run.

## Executive summary

The repository is in good shape for its current scope: the complete `TripleG3.P2P.slnx` builds cleanly and all 68 tests pass. Transport hardening, versioned serialization, RTP lifecycle work, and package validation already address many earlier risks.

The main remaining opportunities are product/API clarity and release confidence rather than an immediately demonstrated build failure. The highest-value work is to make the release workflow prove the same artifact it publishes, define a stable transport error/result contract, and add fuzz/property tests around untrusted wire input.

## Validation performed

- `dotnet build TripleG3.P2P.slnx --configuration Release`: passed with no warnings.
- `dotnet test TripleG3.P2P.slnx --configuration Release --no-restore`: 68 passed, 0 failed, 0 skipped.
- Working tree was clean at review time.

## Prioritized findings and recommendations

### P1 — Release CI does not run integration tests or package-consumer validation

**Evidence:** `.github/workflows/TripleG3-P2P-release.yml` restores, builds, and tests only `tests/TripleG3.P2P.UnitTests/TripleG3.P2P.UnitTests.csproj`; the repository contains a separate integration test project covering UDP, TCP, timing, DI, and video network behavior.

**Risk:** A release can pass while a socket, lifecycle, or cross-component regression remains undetected. The local full solution is green, but the publish gate is weaker than the repository's own validation command.

**Recommendation:** Add a release-gate integration job, preferably on a stable OS matrix if required by the socket tests. Keep the current fast PR unit job, but run integration tests before pack/push. Add a small consumer smoke test that references the packed `.nupkg` from a temporary project and verifies public API resolution.

### P1 — Artifact versioning and restore inputs are not fully aligned

**Evidence:** The workflow computes an ephemeral version after restore, then builds the unit-test project with `-p:Version=...` and packs the library with `--no-build`. The package project is reached through a project reference, but the workflow does not explicitly build the package project as its own release artifact or verify that the packed assembly's informational/version metadata matches the computed package version.

**Risk:** Future MSBuild changes can produce a package whose package version, assembly version, symbols, or generated metadata are inconsistent while the current package checks still pass.

**Recommendation:** Build/pack the package project explicitly with the computed version, run tests against the same build output, and assert package version plus assembly informational version in validation. Avoid relying on transitive project-build behavior for the published artifact.

### P1 — Transport delivery semantics are underspecified for partial failure

**Evidence:** `UdpSerialBus` and `TcpSerialBus` throw only when every destination fails and otherwise log partial failures. `ISerialBus.SendAsync` returns no delivery result.

**Risk:** Callers cannot know which endpoints succeeded, whether a retry is needed, or whether a partial broadcast is acceptable. This is especially important for TCP, which is documented as reliable but can have multiple configured targets.

**Recommendation:** Preserve the existing interface for compatibility, but add an opt-in result API such as `SendReport`/`SendManyAsync` containing attempted, succeeded, failed, and endpoint-specific exceptions. Document that existing `SendAsync` means “at least one destination accepted the frame,” or change behavior in a major version.

### P1 — Untrusted-input testing should be property/fuzz based

**Evidence:** Wire parsing is covered by focused tests, but the public transports parse attacker-controlled UDP/TCP bytes and use reflection, serializers, payload limits, and nested contracts. The current suite does not appear to include a sustained random malformed-frame campaign or allocation/time budgets.

**Risk:** Parser edge cases can cause CPU amplification, unexpected exceptions, pool pressure, or compatibility regressions even when example-based tests pass.

**Recommendation:** Add property-based or deterministic fuzz tests for headers, length-prefixed frames, JSON/type-name extraction, RTP headers/extensions/padding, and malformed nested contracts. Assert no process-level exception escapes the receive loop, bounded allocations, and completion within a timeout. Run a smaller corpus in CI and a larger corpus nightly.

### P2 — Protocol configuration validation should be centralized and observable

**Evidence:** `ProtocolConfiguration` has required endpoints/ports, payload and connection limits, and a serialization protocol, while validation is implemented inside transport classes. The two transports can evolve different validation behavior.

**Risk:** Invalid values may fail at different times or with different exceptions depending on transport. This complicates configuration diagnostics and host startup validation.

**Recommendation:** Add a public `Validate()`/`ProtocolConfigurationValidator` that validates port ranges, non-null endpoints, address-family compatibility, positive limits, supported enum values, and duplicate endpoints. Call it from both transports and provide structured error messages suitable for options validation.

### P2 — The public serialization contract should expose compatibility/version policy more clearly

**Evidence:** `SerializationProtocol.None` is delimiter-based and retained for compatibility, while `LengthPrefixed` is recommended for new contracts. The serializer contract and README describe the formats, but there is no explicit protocol-version negotiation or serializer capability handshake.

**Risk:** Two peers can select different serialization protocols or evolve a contract incompatibly without a clear negotiation failure. The bus currently treats the configured protocol as an out-of-band agreement.

**Recommendation:** Add a protocol capability/handshake option or document a mandatory deployment contract. Include schema/version identifiers in the length-prefixed envelope and expose serializer compatibility diagnostics. Keep `None` unchanged for existing peers.

### P2 — API surface and package targeting should be made intentional

**Evidence:** The library targets only `net10.0`, while README positioning mentions “.NET 10 / MAUI apps.” MAUI/platform heads are described as sibling projects but are not part of this repository. The library also has canonical video APIs plus obsolete compatibility wrappers.

**Risk:** Consumers may assume MAUI-specific support or broader .NET compatibility than the package provides. The duplicate video surface increases documentation and binary-compatibility cost.

**Recommendation:** State clearly that this is a platform-neutral net10 library consumed by MAUI hosts. Consider a multi-targeting decision (`net10.0` only versus additional supported TFMs) based on actual API dependencies. Track removal of obsolete `Video.Rtp` wrappers in a 2.0 issue and add API compatibility checks before release.

### P3 — Improve observability and operational diagnostics

**Evidence:** Transport receive/send paths use `ILogger`, but the public API exposes only `IsListening`, and video/transport statistics are not unified into a diagnostic contract.

**Recommendation:** Add optional counters/metrics for received, rejected, malformed, dropped, sent, partial, and failed frames; expose them through immutable snapshots. Use `System.Diagnostics.Metrics` alongside logging for host integration, without logging payload contents or secrets.

### P3 — Documentation and samples could better demonstrate production-safe usage

**Evidence:** The README has strong basic examples, but the main quick start uses `SerializationProtocol.None`. Production concerns such as cancellation, disposal, payload limits, authentication/authorization, retries, and endpoint trust are not prominent in the first path.

**Recommendation:** Make `LengthPrefixed` the primary new-application example, include `await using`/shutdown patterns, show explicit payload limits, and add a security/deployment section.

## Suggested implementation order

1. Strengthen release CI with integration tests and packed-package consumer validation.
2. Define/document delivery result semantics and add an opt-in detailed send report.
3. Add deterministic fuzz/property tests for all public wire parsers.
4. Centralize configuration validation and expose diagnostics/metrics.
5. Finish the 2.0 video API migration plan and remove obsolete compatibility wrappers when appropriate.
6. Refresh README examples and clarify target framework/platform support.

## Conclusion

No immediate build or test failure was found. The repository is release-capable for its current tested behavior, but the release pipeline should be brought up to parity with the full local solution before treating every main-branch push as production-ready. The remaining code improvements are primarily about explicit contracts, malformed-input resilience, operational visibility, and reducing misleading public API surface.
